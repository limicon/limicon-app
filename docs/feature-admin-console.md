# Admin console

The Organizing Team's console at `/admin` (ADM-1). It covers the current edition: the one with the latest year. Its user and session pages follow the Festival platform's admin console (`reference-festival.md` → 5.8 and 9.7).

Status: draft, 2026-11-19. Built: Overview, Settings, Users, Orders, Guests, Sessions, Website, FAQ, Policies and Team (with roles), and editing the website on the site itself. Discount codes, forms, emails, and the sessions and form-response exports come with the features they manage.

## Access

- Access comes from **roles** (`admin_permissions` rows naming `admin_roles`). A person may hold several, and their privileges add up. Holding any role opens the console and the Members area; a signed-in person with none gets a plain 404, and a visitor goes to sign in (`requireAdmin` in `app/middleware/services.server.ts`). Only role holders see an **Admin** button: last in the public site's menu, and in the Members area's menu.
- All admins hold the built-in **Admin** role, which has every privilege, including ones added later, and can't be edited or deleted. Other roles give particular privileges, listed in `app/lib/admin-roles.ts`: see orders and money (`orders`), edit settings (`settings`), view and reply to team@limicon.org emails (`inbox`), send emails from team@limicon.org (`email`), edit the website (`website`) and post updates to the website (`updates`: add content but not remove it). **Bookkeeper** (see orders and money) is the first. The inbox, sending and updates privileges are ready for those features, which aren't built yet.
- Each console page checks its privilege (`requirePrivilege`), and the menu shows only the pages a person's roles allow. Users, Guests, Sessions and Team are for admins only. Every role holder sees the Overview's counts; revenue, buyers and incomplete purchases need `orders`. Editing the website on the site itself needs `website`.
- Admins add and edit roles, and give them by email, on the Team page (**+ Add role** on the Users page too) and set anyone's roles with checkboxes on the Users list or the person's page. They can make anyone an admin but can only remove admin status from themselves, and only while another admin remains. Nobody can deactivate an admin or themselves, so the team can't lock itself out.
- Removing anyone from a role, by unticking it and saving or with **Remove** on the Team page, first opens a dialog asking why. Remove stays disabled until a short reason (up to 300 characters) is typed, and Cancel changes nothing. The server refuses a removal without a reason too (`checkRoleChange`). Each removal is kept in `admin_role_removals` with the role's name at the time, who removed whom, when and why. Admins read it as **Role history** on the person's page and **Recent removals** (the last 20) at the foot of the Team page. Adding roles needs no reason.
- People's roles show beside their name: in the console, and beside your own email in the Members area. The directory (PRO-5) will show them too.
- A deactivated account (`profiles.deactivated_at`) can't open the Members area or the console, whatever it holds (MSG-4). Its data stays.

## Pages

| Page | What admins do there |
| --- | --- |
| Overview | The four totals (ticket holders, revenue, accounts, admins); **incomplete purchases**, flagged in red: everyone whose checkout is still pending, with their email and when they started, newest first; the same four totals for the last 7 days, which open to list who bought that week; registrations per week; and this year's sessions. |
| Settings | In order: **the event** as the public sees it (PUB-2): name, teaser, start and end each with a time zone (visitors see them in their own zone), image (Upload, then Change or Delete) and About, with Save or Cancel; **tickets**: comp tickets for an existing account (REG-9), issued as an order of one, and a preview of the registration form with **Edit** to reword, reorder, remove and add fields (short answer, long answer, checkbox optionally linking to a page, headline or paragraph text); **ticket tiers** (REG-3); the registration and calendar **switches** (REG-10, CAL-9); and **member links** (MEM-2, with "Add new link"). |
| Users | Every account, searchable and filtered by ticket status, role (any admin, hosts, no role, or one role) and active or deactivated, with a CSV download. Each person's roles are checkboxes in the list. Each person's page shows when they joined and last signed in, their tickets (with Remove for a comp), roles, sessions, RSVPs and registration answers. Admins edit their name, set their roles, deactivate or reactivate the account, and keep private notes. Admins also see the person's role history: each removal, by whom and why. |
| Orders | The number of orders, tickets bought (paid orders; each order is one ticket for the buyer) and revenue, then every order: name, order date, ticket (tier), status (paid in green, incomplete in red) and price ("Comped" for comps). Click a heading to sort by it, again to reverse. Search, filter by status (incomplete ones are checkouts to follow up) and ticket, and download with a checkbox per column. |
| Guests | How many people hold a ticket, then each one: name, email (a mail link), address from their registration and a link to their profile. First-name order, switchable to last name; search; download with a checkbox per column. |
| Sessions | Every session, drafts included, filtered by status or co-creation. Admins edit any session in the hosts' editor inside the console, publish, take off the calendar or delete it (SES-4), and see its hosts and RSVPs. The editor's **This is a co-creation meeting** box marks co-creation meetings (SES-9). |
| Website | The public website's pages (PUB-1, PUB-2): add a page, edit it on the website or here, put it in or out of the menu, order the menu, publish or unpublish, delete. **✎ Edit website**, at the foot of the menu, opens the home page in edit mode. |
| FAQ | The public `/faq` page's questions and answers (PUB-1), added and updated as questions come in: each question has an **Edit** button that opens it in place. |
| Policies | The Privacy Policy and Code of Conduct, each with **Edit**, which opens it in the rich text editor; saved changes show on `/privacy` and `/conduct` straight away. Until a policy is first edited, its page shows the text in `app/content/policies.tsx`. |
| Team | Each role in turn, Admin first: what it may do, **+ Add** that role at the top right, and a box listing who holds it (with who added them and when) and invitations waiting for a first sign-in. Adding an email with an account gives the role at once; otherwise it waits in `admin_invitations` until that address first signs in. No email is sent. **Edit role** opens a role's name and a checkbox per privilege, and **+ Add new role** at the foot adds one. Admin is built in; a role someone holds or is invited to can't be deleted. **Recent removals** at the foot lists the last 20 removals from roles, with who removed whom and why. |

The calendar switch is stored, but the schedule and Host a session pages don't act on it yet. Members don't see the member links yet either. Checkout isn't built, so nothing creates paid or pending orders yet; until then the Orders page shows comps and any imported tickets.

## The website builder

- Every public page except the fixed ones (sign-in, account, tickets, FAQ, policies) is a `site_pages` row built from sections: text, image, image and text, columns, buttons, and the event (its image, name, teaser, dates and About from the Settings page). The front page is `home` at `/`; others are at `/<address>`. Each section has a plain, tinted or dark background.
- Admins edit a page in two places with the same editor (`components/page-editor.tsx`): on the page itself, through the **Edit this page** button only admins see (`?edit=1`), and in the console at `/admin/website/<address>`. The editor lays sections out as the page will look, with **+ Add section** between them, ↑ ↓ and Remove on each, and page settings (title, address, menu name, in menu, published). Save or Cancel.
- Unpublished pages are drafts only admins can open. Published pages in the menu appear in the console's order, before FAQ and Members, and in the footer's site map.
- The editor posts the sections' order as JSON and each section's content as fields named `<field>:<id>`; `readPageForm` in `app/lib/site-pages.ts` rebuilds the sections, keeping only what each kind uses.

## Rich text and uploads

- The rich text editor (`app/components/rich-text-editor.tsx`, TipTap) offers bold, italic, underline, strikethrough, headings, lists, quotes, alignment, links, emoji, images and file attachments. It loads only in the browser: TipTap can't run in the Worker. `vite.config.ts` pre-bundles its packages, because Vite otherwise finds them late and loads a second copy of React in development.
- Documents are stored as TipTap JSON, never HTML. `cleanRichText` in `app/lib/rich-text.ts` keeps only the nodes, marks and attributes `components/rich-text.tsx` draws, and allows links only to the web, email and the site's own pages, and images only from the media bucket or https.
- Admins upload images and files through `/admin/upload` into the R2 bucket `limicon-media` ([`config-cloudflare.md`](config-cloudflare.md)), served at `/media/<key>`. Allowed types are images (not SVG), PDF, text and office documents, up to 10 MB each, listed in `app/lib/media.ts`. Replacing the event image deletes the old one; files removed from rich text stay in the bucket.

## Code

- `app/routes/admin/`: the layout and one route per page, plus the CSV downloads (`*-csv.ts`) and `upload.ts`. `app/routes/media.ts` serves uploads.
- `app/lib/admin.server.ts`, `admin-users.server.ts`, `orders.server.ts`, `event.server.ts`, `site-documents.server.ts`, `site-pages.server.ts`, `admin-roles.server.ts`, `registration.server.ts` and `faq.server.ts`: the queries, tested against the local database. `page-route.server.ts` loads and saves a page for the public routes and the console.
- `app/lib/admin-forms.ts`, `admin-roles.ts`, `admin-tables.ts`, `admin-users.ts` and `registration-form.ts`: form checks, table columns, filters and sorting, shared by pages, downloads and queries.
